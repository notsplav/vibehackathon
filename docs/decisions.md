## Решения

### 2026-10-26 — Версия для Firefox из общего кода

- **Что изменено:**
  - **Сборка.** `npm run build:extension` собирает два варианта: `extension/dist` (Chrome) и `extension/dist-firefox` (Firefox 128+). Манифест Firefox получается из манифеста Chrome функцией `firefoxManifest` (`extension/scripts/manifest.ts`):
    - фон — `background.scripts` (event page) вместо service worker;
    - `sidebar_action` вместо `side_panel`;
    - `browser_specific_settings.gecko.id = sverka@vibehackathon`;
    - без `key`, `minimum_chrome_version` и разрешения `sidePanel`.
  - **Различия API** собраны в `extension/src/platform.ts`:
    - `browser` или `chrome`;
    - открытие панели: `sidebarAction.open()` или `sidePanel.open()`;
    - настройка панели только в Chrome.

    Причина отключения порта читается из `port.error` (Firefox) или `runtime.lastError` (Chrome). Текст «No such native application» распознаётся как «помощник не установлен».
  - **Помощник** регистрируется в обоих браузерах (`npm run install:host`). Для Firefox — манифест в `~/Library/Application Support/Mozilla/NativeMessagingHosts/` с `allowed_extensions: ["sverka@vibehackathon"]`.
- **Почему:** запрос владельца. Код и логика общие; отличаются только ключи манифеста и вызовы, специфичные для браузера.
- **Риски и проверки:**
  - **Фон в Firefox** выгружается при простое. По тестам самого Firefox открытый порт Native Messaging этому мешает (`test_ext_native_messaging_geckoview.js`), видимая боковая панель — тоже (MDN, Background scripts). Если проверку всё же прервёт выгрузка, она будет помечена прерванной, как в Chrome.
  - **Неподписанное расширение** в обычном Firefox устанавливается только как временное, до перезапуска браузера.
  - **Подсветка фрагмента** (CSS Custom Highlight API) включается только там, где браузер её поддерживает. Без неё карточка работает.
- **Кто принял решение:** владелец репозитория.
- **Затронутые контракты:** манифест помощника (добавлен Firefox, `allowed_extensions`), ID расширения в Firefox.

### 2026-10-26 — Проверка через Claude Code и помощника Native Messaging вместо сервера

- **Что изменено:**
  - **Удалено:** локальный сервер (HTTP API, SQLite, адаптеры Gemini и Ollama, поиск SearXNG и Ollama Web Search, страница настроек провайдеров), конфиг SearXNG, `.env.example`, зависимости `@google/genai` и `zod`.
  - **Новая схема:** расширение → помощник `host/` (Node.js, Native Messaging; браузер запускает его только на время проверки) → `claude -p` под учётной записью пользователя в Claude Code.
    - Утверждения выделяет `haiku` без инструментов, по `--json-schema`.
    - Каждое утверждение проверяет `sonnet` с `WebSearch`, по 5 одновременно.
    - Короткую сводку пишет `haiku`.
  - **Что сохранено:** чистая логика перенесена в `core/` — проверка ответов модели (точные фрагменты, объединение дубликатов, выделенный фрагмент), правило вердикта и статистика. Без изменений остались извлечение статьи, маркеры, карточки, панель и проверка выделенного.
  - **Источники** — только URL из результатов `WebSearch` (`tool_use_result` в `stream-json`). Ссылки, которые модель написала сама, но которых не было в поиске, отбрасываются. Если модель ответила без поиска, проверка повторяется один раз с требованием искать. Без ссылки из поиска вердикт понижается до `insufficient`.
  - **Изоляция `claude`:**
    - белый список `--tools` (+ `--allowedTools` для разрешения);
    - `--setting-sources ""` — без пользовательских настроек и хуков;
    - `--strict-mcp-config`, `--no-session-persistence`;
    - пустая временная папка;
    - чистое окружение: `HOME`, `USER`, `LOGNAME`, `PATH`, `LANG`. Без `USER` и `LOGNAME` Claude Code не читает вход из Связки ключей macOS (воспроизведено);
    - `--max-budget-usd 0.5`.

    Режим `--bare` не подходит: в нём не работает вход по подписке, только `ANTHROPIC_API_KEY`.
  - **Хранение.** Состояние проверок — в `chrome.storage.local`: его пишет фоновый скрипт, панель следит через `storage.onChanged`. Если Chrome перезапустил фоновый скрипт посреди проверки, она помечается прерванной.
  - **Разрешения расширения:** добавлено `nativeMessaging`, убран доступ к `http://127.0.0.1:8787/*`.
- **Почему:**
  - Владельцу важна скорость, а держать Docker с SearXNG и локальные модели неудобно. Токены Claude он готов тратить.
  - **Замер на эталоне Lenta** (11 утверждений): около 90 с и $0,62 против нескольких минут на `qwen3:14b`. Плюс SearXNG блокировали поисковики.
- **Отступление от ТЗ:** ТЗ (разделы 4, 7, 8, 9) описывает локальный сервер, SQLite и Gemini с grounding. Принцип «источники только из метаданных поиска» сохранён, изменились исполнитель и хранение.
- **Кто принял решение:** владелец репозитория. **Команду нужно предупредить:** сервер и его API удалены, `CLAUDE.md` обновлён.
- **Затронутые контракты:**
  - удалены HTTP API и схема SQLite;
  - новые сообщения помощника — `shared/host.ts`;
  - записи `page:<url>` и `analysis:<id>` в `chrome.storage.local`;
  - удалены типы `HealthResponse`, `CreateAnalysisResponse`, `ServerSettings`, `SettingsResponse`.

### 2026-10-25 — Проверка выделенного фрагмента

- **Что изменено:**
  - **Как запустить.** Пункт контекстного меню «Сверка: проверить выделенное» (новое разрешение `contextMenus`) или кнопка «Проверить выделенное» в панели.
  - **Что проверяется.** Утверждения берутся только из выделения. Если выделена часть предложения, берётся утверждение этого предложения: достаточно общего куска не короче половины фрагмента утверждения (минимум 40 символов).
  - **Контекст.** Заголовок, подзаголовок, до 2 абзацев перед выделением (не больше ~1200 символов) и 1 после. Он помогает модели раскрыть местоимения, даты и субъекты, но утверждения из него не выделяются. Сервер дополнительно отбрасывает вхождения вне выделенных блоков.
  - **Объём данных.** На сервер уходят только выделенные блоки и контекст, а не вся статья.
  - **Выделение вне найденной статьи** (сайдбар, страница без статьи): блоком становится абзац с выделением, контекстом — соседние абзацы и `h1` или `<title>`.
  - **Повтор проверки** (↻) проверяет тот же фрагмент по сохранённому тексту, а не новое выделение.
- **Почему:** пункт P2 ТЗ («выбранный пользователем фрагмент»); запрос владельца.
- **Кто принял решение:** владелец репозитория.
- **Затронутые контракты:**
  - API: необязательное поле `ExtractedArticle.focus` и поле `AnalysisState.focus`;
  - SQLite: миграция 6, `analyses.focus_json`. Выделение входит в хэш, поэтому у каждого фрагмента своя запись кэша;
  - разрешения расширения: `contextMenus`.

### 2026-10-25 — Страница настроек: провайдер, модель, поиск

- **Что изменено:**
  - **Страница настроек расширения** (`options_ui`, нативная страница Chrome). Открывается из «Параметров» в `chrome://extensions` и шестерёнкой в панели. На ней выбираются:
    - провайдер (Ollama или Gemini) и модель из доступных: список моделей Ollama берётся из `/api/tags`, моделей Gemini — из API;
    - поиск для Ollama (SearXNG или Ollama Web Search) и поисковики SearXNG;
    - число запросов на утверждение (1–3).
  - **Новые маршруты:** `GET /api/settings` (настройки и варианты) и `PUT /api/settings`. PUT принимается только с `Origin` расширения и проверяется по схеме и по списку доступных вариантов.
  - **Хранение.** Настройки лежат в SQLite (миграция 5, таблица `settings`) поверх значений по умолчанию из `.env`.
  - **Применение.** Новые анализы сразу идут с новыми настройками, идущие доработают со старыми.
  - **Ключи API** через страницу не передаются и не хранятся в базе.
  - **Поисковики SearXNG** передаются в каждом запросе параметром `engines`. Так можно включать и выключенные по умолчанию (проверено на `engines=yep`), не трогая конфиг SearXNG.
- **Почему:** переключать провайдера и поиск через `.env` с перезапуском сервера неудобно.
- **Кто принял решение:** владелец репозитория.
- **Затронутые контракты:** API (`ServerSettings`, `SettingsResponse`, `GET/PUT /api/settings`), SQLite (миграция 5).

### 2026-10-25 — Ускорение Ollama: запросы при извлечении, параллельный поиск; устойчивость SearXNG

- **Что изменено:**
  - **Запросы при извлечении.** Провайдер Ollama составляет поисковые запросы вместе с извлечением утверждений: в схеме ответа появилось поле `searchQueries`. Запросы хранятся в SQLite (миграция 4, `claims.search_queries_json`), поэтому после перезапуска сервера их не нужно составлять заново.
  - **Один вызов модели на утверждение** (вердикт) вместо двух. Отдельный вызов для запросов остаётся запасным вариантом, если запросов нет.
  - **Параллельный поиск:** запросы одного утверждения ищутся одновременно.
  - **SearXNG:**
    - дополнительно включены `google`, `bing`, `yahoo`, `yandex` и `qwant`;
    - сокращено время блокировки поисковика после ошибок (60–300 с вместо 180–3600 с).
  - **Ошибка поиска не превращается в вердикт.** Пустой ответ SearXNG при заблокированных поисковиках (`unresponsive_engines`) теперь техническая ошибка `rate_limited` с понятным текстом. Раньше он превращался в вердикт «Недостаточно данных».
- **Почему:**
  - **Скорость.** Идея описана в README ветки `Codex_vibe` (kakugoo). Кода в той ветке не было, поэтому README оттуда не переносился, а реализация сделана здесь.
  - **Замеры на `qwen3:14b`** (эталон Lenta, M5 Pro):
    - отдельный вызов для составления запросов — 2,6–3,3 с на утверждение;
    - извлечение с запросами не медленнее: 52–53 с против 58–60 с без запросов;
    - проверка одного утверждения — около 12 с.
  - **Полнота извлечения.** Число утверждений колебалось от 5 до 7 между прогонами в обоих вариантах, систематической потери не видно (выборка маленькая).
  - **Поиск.** Во время работы все включённые по умолчанию поисковики SearXNG оказались заблокированы (brave, duckduckgo, google cse, wikipedia). Поиск возвращал пустые ответы, и утверждения ошибочно получали вердикт `insufficient`.
- **Кто принял решение:** владелец репозитория.
- **Затронутые контракты:** SQLite (миграция 4). API не менялся.

### 2026-10-25 — Вместо плашки «Предварительный результат» — «Анализ идёт · время»

- **Что изменено:** отдельная плашка «Предварительный результат» в панели убрана. Пока анализ не завершён, наверху горит одна плашка «Анализ идёт · 2:34». После завершения на её месте «Готово», «Остановлен» или «Отменён». Поле `AnalysisState.preliminary` в API осталось без изменений.

- **Кто принял решение:** владелец репозитория.
- **Затронутые контракты:** нет.

### 2026-10-25 — SearXNG вместо Ollama Web Search, 2 запроса на утверждение, повторное использование проверок

- **Что изменено:**
  - **Поиск сменный** (`SEARCH_PROVIDER`). По умолчанию используется локальный SearXNG в Docker (`npm run searxng:up`, образ `searxng/searxng:2026.9.30-a9d990033`, порт только на `127.0.0.1`). Ollama Web Search остаётся вариантом.
  - **Конфиг SearXNG** — `searxng/settings.yml`: включён формат JSON, `limiter` отключён. `secret_key` при каждом запуске генерируется заново и в репозитории не хранится.
  - **2 поисковых запроса на утверждение** вместо 3 (`SEARCH_QUERIES_PER_CLAIM`).
  - **Одинаковые утверждения проверяются один раз.** Внутри статьи они объединялись и раньше. Теперь результат последней успешной проверки такого же утверждения той же моделью за `CLAIM_REUSE_HOURS` (по умолчанию 24 ч) копируется вместе с источниками; к объяснению добавляется пометка, откуда взят результат. «Повторить анализ» (`force=1`) проверяет всё заново.
  - **SQLite, миграция 3:** столбцы `claims.claim_key` и `analyses.fresh`.
- **Почему:** бесплатные лимиты Ollama Web Search (они не опубликованы) кончались на одной статье: до 3 запросов на каждое утверждение.
- **Риски:**
  - SearXNG собирает выдачу Google, Bing и других поисковиков, и они могут временно ограничивать частые запросы. Ошибку будет видно в состоянии claim.
  - Повторно использованный результат может устареть в пределах окна переиспользования.
- **Кто принял решение:** владелец репозитория.
- **Затронутые контракты:** SQLite (миграция 3). API не менялся.

### 2026-10-25 — Живой ход анализа в API и панели

- **Что изменено:**
  - **Новое поле `AnalysisState.live`** (`LiveProgress`). Пока анализ идёт, в нём видно, сколько частей статьи уже прошло этап A, и какие утверждения проверяются прямо сейчас: шаг (`queries` / `search` / `verdict`), время начала и поисковые запросы. Данные хранятся только в памяти сервера и в SQLite не пишутся. У завершённого анализа и у анализа, ожидающего возобновления после перезапуска, `live` равен `null`.
  - **Интерфейс `FactChecker.checkClaim`** получил необязательный колбэк шагов.
  - **Сервер пишет в консоль этапы:** сколько найдено утверждений, вердикт и время для каждого claim, итог анализа.
  - **Панель показывает:**
    - шаги этапов;
    - блок «Сейчас»: какое утверждение проверяется, на каком шаге, с какими запросами;
    - общий таймер и «обновлено N с назад»;
    - полосу по вердиктам;
    - оценку оставшегося времени.
  - **Страница:** проверяемый блок мягко пульсирует. При `prefers-reduced-motion` анимации отключены.
- **Почему:** по одним статусам claims было непонятно, на каком этапе анализ, особенно на медленной локальной модели.
- **Кто принял решение:** владелец репозитория.
- **Затронутые контракты:** API (`AnalysisState.live`, тип `CheckStep`).

### 2026-10-25 — Второй провайдер: локальная модель Ollama с Ollama Web Search

- **Что изменено:**
  - **Выбор провайдера.** Кроме Gemini, сервер умеет работать с локальной моделью через Ollama. Провайдер выбирается переменной `LLM_PROVIDER=gemini|ollama`, по умолчанию `gemini`, как в ТЗ. Модель Ollama по умолчанию — `qwen3:14b`.
  - **Как идёт проверка в Ollama:**
    1. локальная модель составляет 1–3 поисковых запроса;
    2. Ollama Web Search (`POST https://ollama.com/api/web_search`, ключ `OLLAMA_API_KEY`) возвращает результаты;
    3. локальная модель выносит вердикт по пронумерованным фрагментам найденных страниц.
  - **Источники.** Ссылки берутся только из результатов поиска, а не из текста модели. Действуют те же правила, что для Gemini: вердикт без источника понижается до `insufficient`, ссылки на сайт самой статьи не считаются подтверждением.
  - **Поле `Evidence.grounding.annotationIndex`.** Для Ollama это номер результата веб-поиска, `interactionId` равен `null`.
  - **Контракт `HealthResponse`.** Вместо `geminiConfigured` теперь `provider` и `problem`. В `problem` — текст причины, по которой проверка невозможна (Ollama не запущена, модель не скачана, нет ключа); если всё готово, `null`.
  - **SQLite, миграция 2.** В таблицу `analyses` добавлен столбец `engine` (провайдер и модель), он входит в ключ кэша. Анализы, завершённые с общей ошибкой (например, исчерпана квота), больше не переиспользуются из кэша.
  - **Повторы.** Проверки останавливаются после двух подряд одинаковых повторяемых ошибок: для 429 — «квота исчерпана», для недоступной Ollama — «Ollama недоступна».
- **Почему:**
  - У ключа Gemini нет квоты на Google Search grounding (см. запись ниже), а продукт нужно проверять уже сейчас.
  - Провайдер выбрал владелец репозитория. Вариант «локальная модель без поиска» отклонён: по ТЗ без источников возможен только `insufficient`.
- **Отступление от ТЗ:** ТЗ называет Gemini с grounding основным путём. Ollama — дополнительный провайдер, Gemini остаётся по умолчанию. Поиск Ollama Web Search не связан с ответом модели так же жёстко, как grounding в Gemini: модель видит только фрагменты страниц, а не полный текст.

### 2026-10-25 — Расширение: маркеры, карточка, панель

- **Что изменено:**
  - **Внедрение content script.** Скрипт внедряется только по действию пользователя: `activeTab` выдаётся нажатием на значок, затем вызывается `chrome.scripting.executeScript`. Статических content scripts и `<all_urls>` нет. Единственное `host_permissions` — `http://127.0.0.1:8787/*`.
  - **Маркеры.** Блок получает атрибуты `data-vh-status` и `data-vh-icon`, в `<head>` добавляется одна таблица стилей: полоса слева, лёгкий фон и значок через `::after`. Узлы в текст статьи не вставляются, ссылки и выделение работают. Для блока с несколькими claims показывается самый осторожный статус.
  - **Карточка.** Карточка открывается в Shadow DOM, текст модели вставляется только через `textContent`. В источниках допускаются только ссылки `http(s)`.
  - **Боковая панель.** Панель запоминает в `chrome.storage.local` пару `analysisId` и отпечаток текста для URL вкладки. При повторном открытии прогресс берётся с сервера. Если текст страницы изменился, маркеры не ставятся и предлагается повторный анализ.
  - **ID расширения.** В `manifest.json` задан публичный ключ `key`, поэтому у всех участников один ID (`gpmhmgppcnmhmkiiaefegfiboaoagiao`). Он же — `ALLOWED_ORIGINS` сервера по умолчанию. Приватный ключ не сохранялся: для локальной установки он не нужен, для публикации в Chrome Web Store потребуется новый.
- **Почему:** этого требуют ТЗ (разделы 4, 10, 11) и правила качества из `CLAUDE.md`: минимальные разрешения, отсутствие модельного HTML на странице, рабочие ссылки.
- **Кто принял решение:** владелец репозитория (единственный разработчик на момент записи).
- **Затронутые контракты:** нет (сообщения панели и content script — внутренние для расширения).

### 2026-10-25 — Локальный сервер: устройство конвейера и API

- **Что изменено:**
  - **Контракт `Claim`:** добавлено поле `occurrences: [{ blockId, exactText }]`. Дубликаты из заголовка, подзаголовка и абзацев объединяются в один claim, и у каждого блока свой точный фрагмент. `exactText` равен фрагменту первого вхождения, `blockIds` вычисляется из `occurrences`.
  - **Проверка claim — два вызова Gemini:**
    1. поиск с `google_search`: ссылки берутся только из аннотаций `url_citation` этого ответа;
    2. вердикт структурированным JSON без инструментов: модель видит отчёт поиска и пронумерованный список источников и может сослаться только на номера из него.
  - **Правило понижения вердикта:** любой вердикт, кроме `insufficient`, без хотя бы одной ссылки из grounding сервер заменяет на `insufficient`. Ссылки на сайт самой статьи не считаются свидетельствами.
  - **Статистика:** `completed` = `checked` + `failed` (обработка завершена), `notCompleted` = `queued` + `checking` + `not_checked`. Мнения считаются отдельно (`opinions`).
  - **429:** все ответы 429 повторяются с задержкой (учитывается `retryDelay`). Если после повторов 429 получают два claim подряд, квота считается исчерпанной: остальные claims помечаются `failed` с понятной причиной, анализ завершается с `error`.
  - **Стек сервера:** вместо Fastify используются встроенные `node:http` и `node:sqlite`, без сторонних зависимостей, кроме `@google/genai` и `zod`.
  - **Защита API:** CORS-заголовков нет, расширение обращается к серверу через `host_permissions`. POST и DELETE принимаются только с разрешённым `Origin` (`ALLOWED_ORIGINS`), `Host` должен быть `127.0.0.1` или `localhost`, тело запроса — `application/json` ограниченного размера.
- **Почему:**
  - Два вызова не зависят от того, поддерживает ли модель schema и grounding в одном запросе. Совместимость пока не проверена: см. запись о квоте grounding ниже.
  - Понижение вердикта выполняет требование ТЗ 12, п. 5.
  - Проверки `Origin`, `Host` и `Content-Type` защищают локальный сервер от запросов со сторонних сайтов и DNS rebinding.
- **Кто принял решение:** владелец репозитория (единственный разработчик на момент записи).
- **Затронутые контракты:** API (`Claim.occurrences`, смысл полей `AnalysisStats`), SQLite (миграция 1).
