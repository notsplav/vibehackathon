# Техническое задание: расширение для проверки утверждений в статьях

Версия: 0.1 · 25 октября 2026 года  
Статус: согласованная основа для разработки MVP

## 1. Цель и границы MVP

Пользователь открывает текстовую новость или статью в Chrome и нажимает кнопку расширения. Расширение извлекает всю статью, выделяет все обнаруженные проверяемые утверждения и постепенно проверяет их через Gemini API с веб-поиском. Проверенные фрагменты отмечаются прямо на странице. Нажатие на фрагмент открывает карточку с выводом, объяснением и источниками. Боковая панель показывает ход проверки, список утверждений и итоговую статистику.

MVP рассчитан на локальную демонстрацию: расширение Chrome Manifest V3 и локальный сервер на компьютере разработчика. Поддерживаются русскоязычные текстовые новости и статьи; архитектура не должна запрещать другие языки. PDF, видео, аудио, изображения с текстом, ленты соцсетей, страницы за авторизацией и публичный рейтинг доменов не входят в первый релиз. Если страница не похожа на статью, интерфейс сообщает об этом без выдуманной оценки.

**Ключевой принцип:** продукт показывает степень подтверждения утверждений доступными источниками, а не объявляет абсолютную истину. «Нет источников» не равно «ложь».

## 2. Пользовательский сценарий

1. Пользователь нажимает кнопку расширения на статье.
2. Открывается боковая панель; расширение извлекает заголовок, автора, дату, текстовые блоки и ссылки. До отправки показывается, что текст статьи будет передан на локальный сервер и далее в Gemini API.
3. Панель показывает прогресс: «статья извлечена», «найдено N утверждений», «проверено X из N». Никакого скрытого ограничения в 10 фактов нет.
4. Проверенные блоки на странице получают неброский маркер. Нажатие на блок открывает карточку; если в блоке несколько утверждений, карточка показывает каждое отдельно.
5. По завершении отображается сводка и статистика по **уникальным утверждениям**. Если работа прервана или часть утверждений осталась без проверки, панель показывает это явно.
6. Пользователь может повторить анализ или удалить локальный результат.

## 3. Статусы утверждений

| Код | Надпись | Когда использовать |
|---|---|---|
| `supported` | Подтверждается источниками | Доступные свидетельства прямо поддерживают утверждение с той же датой, субъектом и контекстом. |
| `contradicted` | Противоречит источникам | Доступные свидетельства прямо противоречат утверждению. |
| `qualified` | Нужна оговорка | Основа утверждения верна, но пропущенное условие, период или контекст существенно меняет впечатление. |
| `disputed` | Источники расходятся | Значимые источники дают разные сведения. |
| `insufficient` | Недостаточно данных | Надёжного вывода сделать нельзя, в том числе когда поиск не дал релевантных источников. |

Отдельные технические состояния: `queued`, `checking`, `failed`, `not_checked`. `failed` означает ошибку обработки, а не ложность факта. Оценочные суждения помечаются как `opinion` на этапе извлечения и не попадают в знаменатель фактической статистики. Высказывание «X заявил Y» проверяется отдельно от истинности Y.

## 4. Архитектура

```text
Chrome MV3 extension
  ├─ content script: извлечение DOM, blockId → DOM-элемент, маркеры и карточки
  ├─ side panel: прогресс, список утверждений, сводка, ошибки
  └─ service worker: запуск сценария и сообщения между вкладкой и панелью
             │ HTTP на 127.0.0.1
             ▼
Local API (Node.js + TypeScript)
  ├─ очередь анализа и ограничение параллелизма
  ├─ Gemini adapter: извлечение утверждений и поиск свидетельств
  ├─ проверка схем, ссылок и привязок к блокам
  └─ SQLite: результаты, статусы, кэш и удаление
```

Секрет `GEMINI_API_KEY` находится только в окружении сервера. Он никогда не включается в код, manifest, сообщения расширения, ответы API или логи. Google рекомендует серверный прокси вместо ключа в браузере: <https://ai.google.dev/gemini-api/docs/api-key>.

Рекомендуемый стек: TypeScript для расширения и сервера, `@google/genai` на сервере, SQLite для локального хранения, Chrome Manifest V3. Gemini Interactions API — основной интерфейс для нового проекта согласно документации Google: <https://ai.google.dev/gemini-api/docs>. Модель по умолчанию — конфигурируемая `gemini-3.8-flash`; не зашивать модель в логику.

Разрешения расширения: `activeTab`, `scripting`, `sidePanel`, `storage` и доступ только к локальному API. Не запрашивать `<all_urls>`. Сервисный worker Chrome может завершаться при простое, поэтому состояние анализа хранится на сервере, а панель переподключается по `analysisId`.

## 5. Извлечение статьи без ИИ

### 5.1. Определение типа страницы и метаданных

1. Прочитать все `script[type="application/ld+json"]` через `JSON.parse`, без `eval`. Поддержать одиночный объект, массив и `@graph`; нормализовать `@type`, включая массив типов и полные URI. Ищем `Article`, `NewsArticle`, `BlogPosting`.
2. Выбрать объект, соответствующий текущей странице: сравнить нормализованные `url` / `mainEntityOfPage` с canonical URL и видимый `<h1>` с `headline`. Не брать объект рекомендованной статьи только потому, что он встретился первым.
3. Для даты публикации использовать `datePublished`, затем `article:published_time`, затем `<time datetime>` рядом с заголовком, затем явную видимую подпись. `dateModified` хранить отдельно. Не использовать дату события в тексте, дату из URL или текущую дату как замену публикации.
4. Для автора использовать `author` выбранного Article-объекта, затем метаданные статьи, затем видимый byline рядом с заголовком. Поддержать одного или нескольких авторов и организацию. Не путать автора с героем публикации.
5. Каждый результат снабжать `source` и качеством `confirmed`, `plausible` или `unknown`; сверять структурированные значения с видимой страницей. Если надёжного значения нет, возвращать `null`.

Поля `author`, `datePublished`, `dateModified` и `headline` описаны в документации Google для Article: <https://developers.google.com/search/docs/appearance/structured-data/article>. Даты из разметки нужно сравнивать с видимой датой: <https://developers.google.com/search/docs/appearance/publication-dates>.

### 5.2. Поиск основного текста

Сначала попытаться выделить корневой контейнер статьи по семантике DOM и совпадению с заголовком. Если это не сработало, использовать `@mozilla/readability` на **клоне** документа как запасной способ определить содержание и метаданные. Readability возвращает title, content, byline и publishedTime, но её `parse()` изменяет переданный DOM: <https://github.com/mozilla/readability>. Для интерактивной подсветки всегда сохранять связь с элементами **исходной** страницы. Нельзя подсветить документ, созданный Readability, вместо живой страницы.

Отбросить `nav`, `aside`, рекламу, комментарии, блоки рекомендаций, скрытые элементы, форму входа и повторяющийся навигационный текст. Проверять итог по минимальной длине, плотности ссылок и сходству с основным текстом Readability. При низкой уверенности показать ошибку извлечения, а не отправлять всю страницу.

### 5.3. Создание блоков

Внутри выбранного корня пройти DOM в порядке чтения. Блоки: заголовок, подзаголовок, абзац, пункт списка, цитата; подпись к изображению хранить как отдельный `caption`, но не проверять по умолчанию. Не дублировать вложенный абзац и его контейнер. Сохранить исходный текст без редакторских исправлений, нормализуя только пробелы для сопоставления.

Каждому блоку присвоить `blockId`. В content script оставить `Map<blockId, Element>`; в сервер отправить `blockId`, `type`, `text`, порядок и связанные ссылки. Длинные блоки можно разделять по границам предложений, сохраняя `parentBlockId`. Отдельные слова и предложения не являются обязательными UI-блоками.

При изменении страницы после анализа сравнить отпечаток текста. Если DOM заменён, не привязывать старый результат к новому тексту; предложить повторный анализ.

## 6. Контракт данных

### 6.1. `ExtractedArticle`

```json
{
  "schemaVersion": 1,
  "url": "https://example.com/news/1",
  "canonicalUrl": "https://example.com/news/1",
  "language": "ru",
  "pageType": "article",
  "metadata": {
    "title": "Заголовок",
    "subtitle": null,
    "authors": [{ "name": "Имя", "type": "person", "source": "jsonld.author", "quality": "confirmed" }],
    "publishedAt": { "value": "2026-10-25T12:16:00+03:00", "source": "jsonld.datePublished", "quality": "confirmed" },
    "modifiedAt": null
  },
  "blocks": [
    { "id": "b1", "type": "paragraph", "order": 1, "text": "Текст абзаца", "links": [] }
  ],
  "extraction": { "status": "ok", "method": "jsonld+dom", "warnings": [] }
}
```

`blockId → DOM-элемент` остаётся в расширении и не сериализуется. Строки статьи — **недоверенный ввод**: команды внутри текста страницы не могут менять системные инструкции или заставлять приложение отправлять данные на произвольные адреса.

### 6.2. `Claim`

```json
{
  "id": "c1",
  "blockIds": ["b1"],
  "exactText": "Точный фрагмент статьи",
  "normalizedClaim": "Одно атомарное проверяемое утверждение",
  "kind": "event|date|number|quote|attribution|other",
  "status": "queued",
  "verdict": null,
  "explanation": null,
  "evidence": []
}
```

Для свидетельства хранить URL, заголовок источника, дату получения, роль (`primary` / `secondary` / `unknown`), краткую связь с утверждением и ссылку на исходную аннотацию Gemini. Ссылки принимать только из метаданных grounding, а не из свободного текста модели. Для каждого claim требуется существующий `blockId`, а `exactText` должен находиться в тексте указанного блока после безопасной нормализации. Дубликаты из заголовка и основного текста объединять в один claim с несколькими `blockIds`.

## 7. Конвейер Gemini

### Этап A: извлечение утверждений

Отправить заголовок, дату публикации, последовательность всех блоков и инструкции: выделить **все** атомарные проверяемые утверждения; отделить факты от мнений; не превращать чужое заявление в подтверждение описываемого им события; сохранять `blockId` и точный фрагмент. Использовать структурированный JSON и проверять его на сервере. Для длинных статей — чанки с перекрытием соседних блоков и последующим объединением дубликатов. Структурированный вывод Gemini допускает схему, но семантические ошибки нужно проверять: <https://ai.google.dev/gemini-api/docs/structured-output>.

### Этап B: поиск и проверка

Для каждого уникального claim запустить запрос Gemini с `google_search`; ограничить параллелизм, например 2–3 запросами, но **не ограничивать количество claims молча**. Результаты сохранять и отдавать по мере готовности. Проверять соответствие субъекта, времени, места и формулировки. Для цитат искать исходную запись/стенограмму и более широкий контекст. Источник, который лишь перепечатал статью, не считать независимым подтверждением. Если достаточной опоры нет — `insufficient`.

Gemini Grounding with Google Search возвращает `url_citation` и сведения о поиске: <https://ai.google.dev/gemini-api/docs/google-search>. Перед реализацией проверить на реальном тестовом вызове сочетание структурированного вывода и grounding у выбранной модели. Если аннотации неудобно сопоставлять с несколькими claim в одном ответе, использовать один проверочный вызов на claim. Не строить продукт на ссылках, которые модель просто написала в JSON.

### Этап C: сводка

Числа считает сервер из сохранённых статусов. Модель может написать 2–4 предложения только по уже сохранённым результатам и с указанием ограничений. Нельзя порождать в сводке новое непроверенное обвинение. Статистика содержит: всего найдено проверяемых, завершено, не завершено, количества по пяти вердиктам и число мнений. До завершения показывать «предварительный результат».

## 8. API локального сервера

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/analyses` | Принять `ExtractedArticle`, вернуть `analysisId` и начальный статус. |
| `GET` | `/api/analyses/:id` | Вернуть прогресс, claims, свидетельства и сводку. MVP может опрашивать endpoint раз в 1–2 секунды. |
| `POST` | `/api/analyses/:id/cancel` | Остановить ещё не начатые проверки; сохранить уже готовые. |
| `DELETE` | `/api/analyses/:id` | Удалить локальный результат. |
| `GET` | `/api/health` | Проверить доступность сервера и наличие конфигурации без раскрытия ключа. |

Сервер слушает только `127.0.0.1`. Разрешённый origin расширения задаётся конфигурацией. Ввод ограничивается по размеру и проходит проверку схемы. Ошибки Gemini, `429`, таймауты и отмена отражаются в состоянии конкретного claim; повторные попытки имеют задержку и предел. API не должен принимать произвольный URL для скачивания сервером в рамках MVP.

## 9. Локальное хранение

SQLite-таблицы: `analyses`, `blocks`, `claims`, `evidence`. У анализа хранить canonical URL, хэш нормализованного текста, время запуска, статус и версию алгоритма. Кэш по URL **и хэшу текста**, чтобы не показывать результат старой редакции статьи. Результат удаляем по запросу пользователя. Публичной базы сайтов и общей оценки домена в MVP нет; схема не должна требовать их появления.

## 10. Интерфейс

Боковая панель: заголовок/дата/автор с отметкой «не удалось определить», прогресс, распределение статусов, список утверждений, краткая сводка, ошибки. Маркеры на странице: нейтральный цвет во время проверки, затем пять доступных цветов/иконок; цвет не является единственным способом различать статус. Карточка по нажатию: исходный фрагмент, вердикт, объяснение, 1–3 релевантных источника и время проверки. Если в одном блоке несколько claims — вкладки или список внутри одной карточки. Ссылки и выделение текста на исходном сайте продолжают работать.

Не вставлять полученный от модели HTML через `innerHTML`; отображать текст безопасно. UI в Shadow DOM или другом изолированном контейнере, чтобы CSS сайта не ломал карточку. Для длинного анализа дать возможность закрыть панель и вернуться к результату.

## 11. Приватность и ограничения

Текст статьи уходит в Gemini через локальный сервер только после действия пользователя. Ключ API остаётся на сервере. Не собирать историю просмотра и не анализировать вкладки автоматически. Не отправлять личные страницы, поля форм, комментарии или текст вне выбранной статьи. Документация Chrome требует минимальных разрешений и прозрачного обращения с данными: <https://developer.chrome.com/docs/webstore/program-policies/policies/>.

Результат нельзя называть «доказанной ложью» только по одному слабому совпадению. Если источники недоступны, страница динамически изменилась, цитата не имеет оригинала или метаданные противоречат друг другу, интерфейс должен сообщить об этом. Продукт не оценивает честность автора или сайта по одной статье.

## 12. Критерии приёмки MVP

1. На предоставленном HTML Lenta.ru извлекаются 7 видимых текстовых блоков: заголовок, подзаголовок и 5 блоков текста; автор, публикация и обновление берутся из совпадающего `NewsArticle` и сверяются с видимой страницей.
2. Рекомендации, меню, подпись к фотографии и боковая колонка не попадают в основной текст.
3. Все выделенные моделью фактические claims получают статус обработки. Дубликаты из подзаголовка и абзацев не увеличивают статистику.
4. Нажатие на помеченный блок открывает относящиеся к нему claims; существующие ссылки страницы работают.
5. Ни один вердикт `supported` или `contradicted` не показывается без релевантной ссылки из grounding metadata. Отсутствие ссылки ведёт к `insufficient` или `failed`.
6. При перезагрузке панели прогресс восстанавливается с сервера. При отмене готовые результаты остаются, остальные отмечены `not_checked`.
7. Пустая страница, страница без статьи, ошибочный JSON-LD, недоступный Gemini, неверный ключ и лимит API отображаются понятными состояниями без падения расширения.
8. Секрет не содержится в репозитории, manifest, клиентском бандле или API-ответах.

## 13. План реализации

**P0 — рабочий путь:** каркас MV3, content script, боковая панель, извлечение DOM/JSON-LD, локальный API, Gemini extraction, grounding проверки, прогресс и карточки.  
**P1 — надёжность:** дедупликация, кэш по хэшу текста, отмена, retry/429, тесты на нескольких сайтах, мобильная/динамическая вёрстка в пределах Chrome desktop.  
**P2 — после MVP:** точная подсветка фразы внутри абзаца, выбранный пользователем фрагмент для нестандартных страниц, история и экспорт, общий рейтинг сайтов, альтернативные модели.

Минимальный набор проверочных страниц: предоставленная Lenta.ru, ещё 3–5 статей с разной разметкой, одна страница без статьи и одна статья без JSON-LD. Разработку начинать с извлечения и привязки блоков: без этого даже хороший ответ Gemini не появится в правильном месте страницы.
